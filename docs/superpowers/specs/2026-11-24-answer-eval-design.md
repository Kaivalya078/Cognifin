# Answer eval + faithfulness (Phase 5, piece 3) — design

Date: 2026-11-24. Branch: `phase-5-eval`.

## Intent

ROADMAP Phase 5: "a ~100-case golden set and a faithfulness score via `verify_citations` + an LLM judge." Today only retrieval is measured (`tests/eval_retrieval.py`: hit@3 0.800, hit@8 1.000 on 40 questions). Nothing measures the answers the user actually reads. This piece adds that, and produces the numbers the public `/engineering` page (piece 4) will show. The project is a demo / portfolio piece; the numbers have to be honest and reproducible, not flattering.

## Goals

- Golden set grows from 40 to ~100 cases, answer key hand-verified (user's choice **A**: I draft and verify each answer on its source page; the user spot-checks ~10).
- One command, run by hand on the user's machine, answers every question through the app's real pipeline, judges each answer, and writes `metrics.json`.
- Faithfulness = share of the answer's claims that a passage it was given supports (claim-by-claim, the same method as RAGAS faithfulness).
- Also reported: correctness against the key, citation validity, retrieval hit@k / recall@60, p50/p95 latency, cost per question, index size.

## Non-goals

- No paid CI: CI does not run this (it needs the full index and an OpenAI key). CI keeps its existing offline gates.
- No new dependency (RAGAS rejected by the user: large LangChain dependency, can't read `chunk_N`/`fin_N` citations; cost was not the reason).
- No cache hit rate: it only means something on a live server; belongs to deploy.
- No change to how answers are produced. The eval measures the app; it does not tune it.

## Anti-goals

- A score graded against an unchecked key.
- Numbers on `/engineering` that can't be regenerated by one command from the committed set.
- Changing the frozen 40-case results: the old 40 stay byte-identical, so the retrieval table in `tests/eval_reports/README.md` stays comparable.

## Constraints

- Cost: generation + judge on gpt-4o-mini, ~$0.20 per full run. The user approved this (local, by hand, no added recurring cost).
- Windows console: set `PYTHONUTF8=1` (emoji crash otherwise).
- The anonymous question limit and auth don't apply (in-process, no HTTP).
- Response cache must be bypassed: `answer_events` reads it first, and pre-warm pins answers for some questions.

## Approaches (user picked 1)

1. **In-process: call `main.answer_question` for each case, then one judge call per answer** — picked. Same retrieval, financials router and prompts a user gets; no server; timings free of network noise. Misses only the thin HTTP/SSE layer.
2. HTTP against a running `/chat/stream` — most realistic (time to first token), but needs the server up and fights the anon limit and the cache. Rejected.
3. RAGAS — rejected (see Non-goals). Estimated ~$0.70–1.00/run for its usual 4 metrics, so cost was not the deciding factor.

## Design

### Golden set v2 (`backend/tests/golden_set.json`)

- `version: 2`, a changelog line. The 40 v1 cases are unchanged (same ids, same fields).
- 60 new cases, my mix (builder may shift a few):
  - every one of the 29 companies with no case today gets at least one;
  - ~15 on FY2026 annual reports (no 2026 case exists);
  - kinds: `table` and `narrative` as today, plus two new kinds:
    - `numeric` (~8): a figure the financials table holds (Q Mar-2025..Sep-2026, FY25/FY26), so the numbers router answers it. `company`/`year` are set; `answer_pages` holds the source page if it is in our PDF corpus, else `[]` (iXBRL source) — such cases are excluded from retrieval hit@k.
    - `refusal` (~5): a question about a listed company the filings don't answer (e.g. a figure no report discloses). Key `answer` is the refusal sentence; `answer_pages: []`. Correct = the app refuses. Guards against hallucinated answers.
- `checked_by`: `["claude", "claude-recheck"]` for my verified cases, plus `"user"` on the ones the user spot-checks. Every new answer is re-found on its page during drafting (recheck = a second pass reading the page text, not memory).
- Spot-check: I pick 10 spread over kinds and companies and give the user the question, the key answer, and the PDF path + page. Any error found → I recheck every case of that kind.
- `test_golden_set.py` updated for v2: version 2; kinds in {table, narrative, numeric, refusal}; pages required only for table/narrative; `test_coverage` → 95–105 cases, ≥ 45 companies, years 2023–2026 present; `test_fully_checked` → v1 ids keep the 3-entry list, new ids have at least `["claude", "claude-recheck"]`.
- Retrieval scorer (`eval_retrieval.py`) skips cases with empty `answer_pages`.

### Runner: `backend/tests/eval_answers.py`

`PYTHONUTF8=1 python -m tests.eval_answers --label <name> [--only <id,...>] [--limit N]`

1. Load the app the way `main` does at startup (corpus, pipeline, financials store), read-only.
2. Check the query settings: the app runs with `INTELLIGENT_PARSING_ENABLED=false` and `MULTI_QUERY_ENABLED=false` (`backend/.env`), so `answer_events` takes the `retrieve_global` path, the same one `eval_retrieval` scores, and generation is the only LLM call per question. The runner exits with an error if either flag is on: the retrieval numbers would then describe a different path, multi-query (temperature 0.7) would make runs vary, and the parser's tokens would escape the cost count. Both flags are recorded in `metrics.json`.
3. Disable the response cache for the run (no reads, no writes).
4. Wrap `main.llm_client` with a recording client for the run only: same model, params and streaming as `generate_stream`, plus `stream_options={"include_usage": True}`; it records the system prompt (which holds the context the model saw), the user message, and prompt/completion tokens. Production code stays unchanged.
5. For each case: `answer_question(question)`; keep answer, citations, `metadata.citation_check`, `metadata.latency_ms`, intent, numcheck results.
6. Judge: one gpt-4o-mini call per answer, `temperature=0`, JSON output (`response_format={"type":"json_object"}`). Input: the recorded context, the answer, the key answer. Output: `{"claims":[{"text","supported":bool,"cited":[ids]}], "correct": "yes"|"partial"|"no", "reason": str}`. A refusal answer has zero claims (faithfulness not applicable). The judge prompt lives in the runner as a constant. For `refusal` cases the judge also answers `"refused": bool` — whether the answer declines to give the figure (e.g. "the report does not disclose X" counts).
7. Per case row: id, kind, company, year, answer, claims, supported count, correct, citation valid/invalid counts, latency, tokens (answer + judge), refused (judge's verdict) and `exact_refusal` (the frontend's strict whole-answer rule from `frontend/src/utils/refusal.js`, ported to Python; this is what shows the upload card).
8. Write the full report to `tests/eval_reports/<YYYYMMDD-HHMM>-<label>-answers.json` (committed, like the existing reports) and the summary to `metrics.json` (below).

Errors: a case whose pipeline raises is recorded as `error` and counted as incorrect; the judge is retried once on invalid JSON, then the case is marked `judge_error` and left out of faithfulness (count reported).

### Scores

- **faithfulness** = Σ supported claims / Σ claims, over answered (non-refusal) cases. Also per kind.
- **correctness** = (yes + 0.5·partial) / cases. Refusal cases: correct iff the judge says the app refused; non-refusal cases where the app refused count as `no`.
- **citation validity** = Σ valid / Σ (valid + invalid) cited ids, from `verify_citations`; plus the share of answers with ≥ 1 citation.
- **refusal**: `refusal_accuracy` = refusal cases the judge marks refused / refusal cases; `upload_card_rate` = refusal cases matching the strict rule / refusal cases (how often a user would actually see the upload card).
- **retrieval**: run the existing `eval_retrieval` scoring over the v2 set (cases with pages), reported both for all and for the v1 40 (must still read hit@3 0.800 — a sanity check that nothing drifted).
- **latency**: p50/p95 of `latency_ms` end-to-end in-process.
- **cost/question**: tokens × gpt-4o-mini prices (constants in the runner, with the date they were checked). With both query flags off, generation is the only LLM call, so this is the full per-question cost; judge cost reported separately.
- One run is published as-is: generation and judge run at `temperature=0` and retrieval is deterministic with the flags off, so reruns differ only by OpenAI's own nondeterminism. No repeated runs.
- **index size**: chunk count, document count, companies, and on-disk size of `index_cache/lancedb`.

### `metrics.json`

Written to `frontend/public/metrics.json` (served statically, so piece 4 just fetches it; works on Vercel with no backend call). Committed. Shape:

```json
{
  "generated_at": "...", "label": "...", "model": "gpt-4o-mini", "judge_model": "gpt-4o-mini",
  "settings": {"intelligent_parsing": false, "multi_query": false, "top_k": 60, "final_k": 8},
  "golden_set": {"version": 2, "cases": 100, "companies": 49, "kinds": {...}},
  "answers": {"faithfulness": 0.0, "correctness": 0.0, "citation_validity": 0.0, "cited_share": 0.0,
              "refusal_accuracy": 0.0, "upload_card_rate": 0.0, "by_kind": {...}, "errors": 0},
  "retrieval": {"hit@3": 0.0, "hit@8": 0.0, "mrr": 0.0, "recall@60": 0.0, "v1_hit@3": 0.0},
  "financials": {"precision": 1.0, "coverage": 0.931},
  "latency_ms": {"p50": 0, "p95": 0},
  "cost_usd": {"per_question": 0.0, "judge_per_question": 0.0},
  "index": {"chunks": 0, "documents": 186, "companies": 49, "disk_mb": 0}
}
```

`financials` is copied from the latest `eval_financials` report (that eval already exists and is offline). The full per-case report stays out of `metrics.json`.

### Results doc

New section "Answer eval results" in `tests/eval_reports/README.md`: the set, the scorer, how faithfulness is judged, and a table with one row per run (first row = this piece's baseline).

## Decided by me (user can override)

- Mix of the 60 new cases, and the two new kinds `numeric` and `refusal`.
- `checked_by` for new cases is `["claude","claude-recheck"]` (+ `"user"` if spot-checked), not the v1 three-entry list.
- `metrics.json` lives in `frontend/public/`.
- Correctness gives `partial` half credit.
- Refusal is judged by the judge (lenient); the strict frontend rule is reported separately as `upload_card_rate`.
- The runner refuses to run with intelligent parsing or multi-query on, rather than measuring those paths.
- Cache disabled and LLM client wrapped inside the runner, not via new production flags.

## Left to the builder

- Judge prompt wording, the recording-client implementation, report filenames, CLI details beyond `--label`/`--only`/`--limit`, how the runner reuses `eval_retrieval`'s scoring functions.
- Unit tests for the pure parts (score aggregation, judge-output parsing, refusal detection) with no API calls; the live run itself is not part of pytest.
